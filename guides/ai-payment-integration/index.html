Field notes from a payments BA

Using AI in business analysis for payment integration

Every PSP integration I've worked on has the same five phases, whether it's Adyen, Klarna, or a legacy gateway. This is where AI has actually saved me hours in each one — and where I still wouldn't let it near the keyboard unsupervised.

Chabila Borkar· Senior Business Analyst, Payments & eCommerce
A quick note before you dive in

I wrote this after one too many conversations where "just use AI for the BRD" turned into three days of untangling a spec that sounded confident and was wrong about half the field-level requirements. It's not a warning against using AI — it's the opposite. I use it constantly. It's a map of exactly where, so you skip the expensive mistakes I didn't.

If you've sat through a PSP certification call, you'll recognise most of this. If you haven't yet — welcome, it's a good kind of chaos.

Part 1 — Fundamentals

The lifecycle doesn't change. Your leverage in it does.

A payment integration is still discovery, contract mapping, sandbox, certification, go-live — in that order, no shortcuts. AI doesn't collapse the phases. It changes how much of each one is spent reading versus deciding.

01 · DISCOVERY & PSP FIT
What I'm actually doing

Scoping which PSP covers the markets and methods we need

Comparing settlement currencies, supported local payment methods, and SCA/3DS handling against the markets in scope — usually across three or four vendor docs at once.

Where AI earns its keep

Pulling method and market coverage out of long PSP capability docs into one comparison table I can sanity-check in ten minutes instead of an afternoon. I still open the source doc for anything going in a contract.

02 · CONTRACT & API MAPPING
What I'm actually doing

Mapping our data model onto the PSP's API contract

Field-by-field mapping between our order/customer schema and the PSP's request/response objects, flagging every mandatory field we don't currently capture.

Where AI earns its keep

A first-pass mapping table from the API reference, done in minutes rather than a day of manual cross-referencing. It gets maybe 80% right — the remaining 20% is exactly the part that needs a human who's read the small print on optional-but-conditionally-required fields.

03 · SANDBOX INTEGRATION
What I'm actually doing

Running test transactions through every state

Authorised, captured, declined, refunded, disputed — walking each path in sandbox and writing up what actually happened versus what the docs promised.

Where AI earns its keep

Turning a stack of raw Postman responses into a readable test log with plain-English notes on anything that deviated from the expected state — the exact task I used to leave until the end of the day because it was tedious, not because it was hard.

04 · CERTIFICATION & COMPLIANCE
What I'm actually doing

Walking the PSP's certification checklist and our PCI-DSS scope

Confirming every mandatory certification scenario is covered and that cardholder data handling stays within scope throughout the flow.

Where AI earns its keep

Drafting the evidence write-up for each checklist item from our test logs. Sign-off itself stays entirely human — this is the one phase where I'd rather be slow and right than fast.

05 · GO-LIVE & RECONCILIATION
What I'm actually doing

Watching the first live transactions reconcile against the ledger

Checking settlement files against internal order records, chasing down anything that doesn't tie out in the first few days live.

Where AI earns its keep

Flagging reconciliation mismatches worth a closer look across thousands of rows, so I'm investigating five real discrepancies instead of scrolling a spreadsheet looking for them.

None of the above replaces knowing the domain. The mapping AI drafts is only checkable because I know what a mandatory 3DS field looks like. Treat the output as a very fast junior analyst's first draft — helpful, occasionally confidently wrong, always reviewed.
Before you touch a model

What I'd tell someone starting this from scratch

01

A good prompt is a scoped requirement

If you can't write the acceptance criteria, you can't write the prompt. Same skill, different output format.

02

PAN and cardholder data don't go in casually

Anything touching PCI-DSS scope needs the same handling rigour whether it's going through a model or a spreadsheet macro. Redact or tokenise before it leaves your system.

03

PSP docs change under you

API versions and field requirements get deprecated. A model's training data goes stale the moment the PSP ships a changelog — always check the doc date.

04

You're still the one who signs off

Certification evidence, mapping sign-off, go-live approval — these carry your name. AI drafts the paragraph; you're accountable for the sentence.

Part 2 — Enhancements

Once the basics are solid, these are worth the setup time

Three techniques that solve specific problems with "just ask the chatbot" once you're doing this at scale — not because they're fashionable, but because each closes a real gap I've hit personally.

Grounding

Retrieval-Augmented Generation

Point the model at your actual PSP API docs, your own past mapping sheets, and prior certification write-ups, and have it answer from those instead of guessing from general training. The difference between "the model assumes a generic 3DS flow" and "the model quotes your PSP's actual mandatory field list from the doc you fed it."

Maps to: Contract & API mapping — draft mappings grounded in the current API version, not a remembered one.
Control

Human-in-the-loop

Certification evidence and go-live sign-off are exactly the checkpoints where an unreviewed AI suggestion could mean a compliance gap or a mis-mapped mandatory field going live. HITL means the workflow pauses and waits for a named reviewer at those points — not everywhere, just where it actually matters.

Maps to: Certification & go-live — the two phases where "mostly right" isn't good enough.
Connection

MCP servers

Model Context Protocol gives an AI assistant live, permissioned access to your own systems — a ticketing tool, an internal API catalog, a reconciliation database — instead of you exporting a CSV every time you need current data. It queries the real thing, scoped to your access.

Maps to: Sandbox testing & reconciliation — live transaction states pulled on demand instead of stale exports.
Part 3 — Hands-on

Building this in Microsoft Foundry

This is the sequence I'd actually follow to wire up the three pieces above as one working assistant, rather than three separate demos. Microsoft Foundry (formerly Azure AI Foundry) is where I'd build it, current as of 2026.

Create a Foundry project and connect your source docs

Stand up a project, then connect your PSP API references, past mapping sheets, and certification write-ups — via Azure Blob Storage or a data connection — ready to be indexed.

Deploy a model from the catalog

Pick a model (e.g. gpt-4o) from the Foundry model catalog as your reasoning engine — swappable later without rebuilding anything else.

Ground it against your own docs (RAG)

Index the PSP references and past write-ups with Azure AI Search, add it to your agent as a knowledge source, so mapping suggestions come back with citations to the actual source doc.

Attach live systems via MCP

From the Foundry portal's Tools menu, add an MCP server connection — a catalog server for your ticketing/DevOps tool, or a custom one exposing read access to your reconciliation data.

Add a human-approval checkpoint

Flag certification evidence and go-live actions as requiring approval. The workflow pauses on a function_approval_request and only proceeds once a named reviewer signs off.

Orchestrate it as a workflow, not a one-shot prompt

Use Foundry's workflow builder to chain retrieval → draft mapping → human review as a repeatable process you can reuse on the next PSP integration.

Evaluate before you trust it, then monitor

Run Foundry's built-in groundedness and relevance evaluations before rollout, then use tracing and Application Insights to see what it's actually doing once it's live.
