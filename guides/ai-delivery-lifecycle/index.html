Field notes from a payments BA

The end-to-end delivery lifecycle, and where AI actually fits

This is the guide that ties the rest of the series together. Same six phases run underneath a new site feature, a technical project, and an operational integration — what changes is who's in the room, what "done" means, and how much risk sits in the release. This walks all three, phase by phase.

Chabila Borkar· Senior Business Analyst, Payments & eCommerce
A quick note before you dive in

I used to think of these as three different playbooks. They're not — it's one lifecycle wearing different clothes depending on whether you're shipping a UI change, migrating infrastructure, or bolting on a vendor's API. Once I started mapping them side by side, the gaps in each one got a lot easier to spot.

Where this guide overlaps with the rest of the series — UAT, payment integration specifics — I've pointed to the deeper dive rather than repeat it here.

Part 1 — Fundamentals

Discovery & framing

Before anything gets written down formally, someone has to decide this is worth doing and roughly what "it" is. What triggers that conversation — and who's in it — is the first real difference between the three delivery types.

New site feature
Technical project
Operational integration
What triggers it
User research, analytics, or a product backlog item gaining priority.
Architecture debt, a scaling ceiling, or a platform roadmap milestone.
A commercial need — a new PSP, carrier, or vendor contract coming into force.
Who's in the room
Product owner, UX, engineering lead.
Enterprise architecture, infra/platform leads, finance (for build vs buy).
Vendor's implementation team, security/compliance, legal for the contract.
Business case shape
RICE-scored against the rest of the backlog.
Cost of inaction vs cost to build — often a multi-year payback case.
Bounded by contract terms and go-live deadline; less discretionary.
Where AI helps
Summarising research/analytics into a first-draft opportunity brief.
Drafting the cost/benefit narrative from raw capacity and incident data.
Turning a vendor's onboarding docs into a scoped first-pass timeline.

Build

The BA's role here is lighter but not absent — mostly keeping scope honest and unblocking ambiguity before it becomes a defect.

Technical project
Operational integration
Rhythm
Sprint-based, frequent demos, feature-flagged incremental release.
Longer build cycles, infra-as-code changes, parallel-run scaffolding.
Sandbox-first, bounded by the vendor's own release/certification calendar.
BA's main job
Clarifying edge cases as devs hit them, keeping scope from creeping.

Where AI helps
Summarising standup/thread ambiguity into a clean clarifying question.
Diffing infra-as-code changes against the design doc for drift.
Digesting vendor sandbox error responses into plain-English blockers.

Release

Where the risk profile of each delivery type shows up most clearly — a feature flag rollback is a config change; an integration cutover can involve a vendor's operations team on a call with yours.

New site feature
Technical project
Operational integration
Rollout shape
Phased/flagged ramp-up, monitored against adoption metrics.
Defined cutover window, often with a change freeze either side.
Coordinated go-live with the vendor, dual-running/verification window.
Rollback plan
Toggle the flag off.
Rehearsed runbook — often the hardest part of the whole project.
Depends on the vendor's own rollback capability — confirm it exists before go-live, not during.
Where AI helps
Drafting the go-live checklist and comms from the release notes.
Flagging gaps in the rollback runbook against the design doc.
Drafting the joint go-live comms and escalation contact sheet.

Operate & monitor

The lifecycle doesn't end at go-live. This phase is where a BA's early involvement either pays off in a clean handover, or doesn't.

New site feature
Technical project
Operational integration
What gets watched
Adoption and conversion metrics against the original business case.
SLOs, error budgets, capacity headroom.
Reconciliation accuracy, vendor SLA adherence.
Feedback loop
User feedback feeds the next backlog iteration.
Incident learnings feed a tech-debt backlog.
Reconciliation exceptions feed an ongoing defect/escalation log with the vendor.
Where AI helps
Summarising qualitative feedback into themes for the next iteration.
Anomaly detection on capacity/error metrics, surfacing what's worth attention.
Flagging reconciliation mismatches across thousands of rows for investigation.
Across all three columns, the same pattern from the rest of the series holds: AI is strongest at compressing volume into something reviewable, and weakest at anything that requires accountability. That's the filter to run every new use case through.
Part 2 — Enhancements

Applied across the whole lifecycle, not one phase

These three show up everywhere above, so it's worth naming them once, properly, rather than repeating the same paragraph six times.

Grounding

Retrieval-Augmented Generation

Every phase above gets more useful when the model is grounded in your actual past projects — ADRs, RAID logs, incident write-ups, prior vendor onboarding docs — instead of answering from general training. The same technique, reused across discovery, design, and operate.

Maps to: every phase — grounded on the specific artefact type that phase produces.
Control

Human-in-the-loop

Business case sign-off, architecture review, go-live decisions, incident severity calls — these repeat across all three delivery types, and every one of them is a checkpoint where an unreviewed AI output is the wrong risk to take.

Maps to: every sign-off point — discovery approval, design review, and release go/no-go.
Connection

MCP servers

Jira, Confluence, your monitoring platform, a vendor's sandbox API — an agent with live, permissioned tool access to all of these can support discovery, build, and operate without you exporting data by hand at every phase.

Maps to: build, release, and operate — where live system state matters most.
Part 3 — Hands-on

Building this in Microsoft Foundry

One assistant, scoped to support the whole lifecycle rather than a single phase — the sequence I'd follow to build it. Microsoft Foundry (formerly Azure AI Foundry), current as of 2026.

Create a Foundry project and connect your delivery archive

Stand up a project, then connect past ADRs, RAID logs, business cases, and incident write-ups across all three delivery types — via Azure Blob Storage or a data connection — ready to be indexed.

Deploy a model from the catalog

Pick a model (e.g. gpt-4o) from the Foundry model catalog as your reasoning engine — swappable later without touching anything downstream.

Ground it against your own delivery history (RAG)

Index the archive with Azure AI Search, add it to your agent as a knowledge source, so drafts across any phase cite your own past decisions rather than a generic pattern.

Attach live systems via MCP

From the Foundry portal's Tools menu, connect Jira/Confluence for live project state, and your monitoring platform for the operate phase — one agent, multiple live tool connections.

Add human-approval checkpoints at every sign-off

Flag business case approval, design review, and go-live decisions as requiring approval. Each pauses on a function_approval_request and only proceeds once a named reviewer signs off.

Orchestrate it as one workflow with phase branches

Use Foundry's workflow builder to model the six phases as stages, with the delivery-type variations (feature / technical project / integration) as branches within each stage rather than three separate workflows.

Evaluate before you trust it, then monitor

Run Foundry's built-in groundedness and relevance evaluations before rollout, then use tracing and Application Insights to see what it's actually doing across a live delivery.

If you're mapping your own delivery lifecycle against this and something doesn't fit — that's usually the interesting part, not a sign I've got the framework wrong. Happy to compare notes.
