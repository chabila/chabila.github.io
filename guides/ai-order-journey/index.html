Field notes from a payments BA

The order journey: cart to cash

Guide 005 covered the customer's experience of fulfilment in one paragraph. This is what actually happens behind that paragraph — the moment a cart becomes an order, the way it splits across warehouses, what WMS is doing while a customer watches a tracking page, and how the money finally gets reconciled at the other end.

Chabila Borkar· Senior Business Analyst, Payments & eCommerce
A quick note before you dive in

This is the part of the stack most BAs never get close to, because it's unglamorous and mostly invisible when it works. I spent years in it — OMS/ERP integrations, a WDSS-to-CorePOS migration, order state machines that had to survive Black Friday without falling over. It taught me that almost every "checkout bug" a customer reports is actually a fulfilment or OTC bug wearing a checkout costume.

Where this overlaps with payment reconciliation, I've pointed back to Guide 002 rather than repeat it.

Part 1 — Fundamentals

Cart-to-order conversion

The exact moment a cart legally becomes an order is where a surprising number of production incidents start — usually because the rollback logic for a failed step was never fully specified.

WHAT'S HAPPENING
What I'm actually doing

Defining the state-transition contract

Specifying exactly what has to be true — payment authorised, inventory soft-allocated, fraud check cleared — before a cart is allowed to become an order, and what unwinds if any one of those fails partway through.

Where AI earns its keep

Drafting the state-transition table from a technical design doc, and summarising failed-conversion logs into a shortlist of the actual recurring causes — usually two or three patterns hiding inside a thousand log lines.

Split shipments

One order becoming three shipments doesn't just triple the tracking numbers — it triples the delivery dates, the partial-refund scenarios, and the ways a customer's expectations can quietly stop matching reality.

WHAT'S HAPPENING
What I'm actually doing

Specifying split logic and partial fulfilment rules

Defining how an order splits across fulfilment nodes based on stock location, and the partial-invoice and partial-refund logic that has to follow it consistently.

Where AI earns its keep

Turning inventory and node data into a first-draft split-shipment test matrix — genuinely tedious to build by hand, and easy for a human to sanity-check once it exists.

WMS fulfilment

Where the order stops being a database record and becomes someone physically walking a warehouse floor — and where OMS and WMS have to agree on what "done" means at every step.

WHAT'S HAPPENING
What I'm actually doing

Mapping pick/pack/ship rules and status sync

Specifying backorder and substitution logic, and making sure WMS status updates (picked, packed, shipped) map cleanly onto OMS order states without gaps or double-counting.

Where AI earns its keep

Turning a WMS vendor's integration docs into a first-pass status-mapping table — the same pattern as PSP field mapping in Guide 002, just a different vendor and a different vocabulary. Summarising warehouse exception reports into recurring causes ops can act on.

Delivery

The last mile is where the customer relationship gets tested most directly — and where the BA's job is making sure the promise made at checkout can actually be kept.

WHAT'S HAPPENING
What I'm actually doing

Specifying carrier routing and exception handling

Defining carrier selection and delivery-promise-date logic, tracking/webhook requirements, and what happens when a delivery fails — wrong address, no answer, refused parcel.

Where AI earns its keep

Clustering delivery exception tickets into categories worth ops attention, and drafting a first-pass carrier API integration mapping — the same shape of work as the WMS and PSP mappings above, at this point a pattern you'll recognise instantly.

Order-to-cash

The stage that closes the loop — and the one where a small upstream inconsistency in any of the previous four stages shows up as a finance team's reconciliation headache weeks later.

WHAT'S HAPPENING
What I'm actually doing

Defining invoicing, recognition, and reconciliation rules

Specifying invoicing triggers, revenue recognition timing, how a return reverses through OMS/WMS/finance simultaneously, and the reconciliation logic between order data and what actually settled.

Where AI earns its keep

Flagging OTC reconciliation mismatches across thousands of transactions for investigation — the same strength that showed up in payment reconciliation in Guide 002, now applied across the fuller order-to-cash dataset rather than just PSP settlement.

Payment-specific reconciliation — settlement files against the ledger, PSP-side mismatches — gets the deeper treatment in Guide 002: Payment Integration. This section is the wider OTC picture it sits inside.
Every stage above traces back to the same root cause when something breaks downstream: a status or amount that two systems disagree about. The whole order journey is, underneath everything else, a reconciliation problem wearing five different costumes.
Before you touch a model

What holds true across the whole order journey

01

The order state machine is the backbone

Every stage above hinges on a well-defined status model. Get the state machine wrong early and every downstream system inherits the ambiguity.

02

Split shipments multiply your edge cases

One order, three shipments, means three delivery dates and three possible partial refunds. The requirements surface is bigger than it first looks — plan for it explicitly.

03

OTC data spans four systems, not one

OMS, WMS, PSP, and finance each hold a piece of the truth. Reconciliation only works once you know which system is authoritative for which data point.

04

A return runs the whole chain backwards

A returned item isn't just a refund — it reverses WMS inventory, OMS order state, and OTC revenue recognition all at once. Model the reverse flow as carefully as the forward one.

Part 2 — Enhancements

Once the basics are solid, these are worth the setup time

The same three techniques from the rest of the series, applied to a part of the stack that's unusually good at generating exactly the kind of volume they're built for.

Grounding

Retrieval-Augmented Generation

Ground the model in your own OMS/WMS integration docs and past reconciliation exception reports instead of general knowledge. The difference between a generic guess at why an order got stuck, and an answer that cites the actual incident from your own system three months ago.

Maps to: WMS fulfilment & OTC — root-cause drafting grounded in your own integration history.
Control

Human-in-the-loop

Credit note approval, manual reconciliation overrides, and backorder cancellation decisions all carry real financial weight. HITL means those specific actions pause for a named human, while routine drafting and pattern-matching keep moving.

Maps to: order-to-cash — anywhere money moves without a customer directly confirming it.
Connection

MCP servers

An agent with live, permissioned access to your OMS, WMS, carrier tracking API, and finance system can trace a single order's actual status across all four — instead of you pulling four separate exports and joining them by hand every time something looks off.

Maps to: every stage — live status tracing across systems that don't naturally talk to each other.
Part 3 — Hands-on

Building this in Microsoft Foundry

The sequence I'd follow to build one assistant that can see an order's full path from cart to cash, not just whichever system happens to be open. Microsoft Foundry (formerly Azure AI Foundry), current as of 2026.

Create a Foundry project and connect your order-journey docs

Stand up a project, then connect OMS/WMS integration docs, carrier API references, and past reconciliation exception reports — via Azure Blob Storage or a data connection — ready to be indexed.

Deploy a model from the catalog

Pick a model (e.g. gpt-4o) from the Foundry model catalog as your reasoning engine — swappable later without rebuilding the rest.

Ground it against your own integration history (RAG)

Index the connected docs with Azure AI Search, add it to your agent as a knowledge source, so mapping and root-cause drafts cite your actual OMS/WMS/carrier setup rather than a generic pattern.

Attach live systems via MCP

From the Foundry portal's Tools menu, connect your OMS, WMS, and carrier tracking API as tool connections, so the agent can pull a specific order's live status across all three rather than working from a stale export.

Add human-approval checkpoints where money moves

Flag credit note approvals and manual reconciliation overrides as requiring approval. The workflow pauses on a function_approval_request and only proceeds once a named reviewer signs off.

Orchestrate it as a cross-system workflow

Use Foundry's workflow builder to chain retrieval → cross-system status trace → drafting → human review, so a single query can follow one order from conversion through cash.

Evaluate before you trust it, then monitor

Run Foundry's built-in groundedness and relevance evaluations before rollout, then use tracing and Application Insights to see what it's actually surfacing once it's live.

If you've untangled a reconciliation mismatch that turned out to trace back three systems and two weeks — I've been there, and I'd genuinely like to compare notes.
