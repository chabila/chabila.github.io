Diagrams · Guide 01

BPMN 2.0, built one level at a time

We model one everyday process, a retail refund request, and make it more realistic in five steps. Each level adds one idea and highlights it in green, so you can see exactly what changed. Beginners can stop at any level; experienced modellers will find the conventions and pitfalls in the later sections.

Chabila Borkar · Senior Business Analyst, Payments & eCommerce
How to read the diagrams

Green outlines and arrows are new at that level. Circles are events, rounded rectangles are tasks, diamonds are gateways, and dashed lines are message flows. You can recreate every diagram in a free tool such as bpmn.io or Camunda Modeler.

The four building blocks

BPMN has over a hundred symbols, but almost every useful diagram is made from four families.

FamilyLooks likeMeansNaming rule
EventsCircle (thin start, double intermediate, thick end)Something that happens: it starts, interrupts or ends the processNoun + past participle: "Refund issued"
ActivitiesRounded rectangleWork that is doneVerb + object: "Review request"

Level 1

A simple sequence

Start, do the work, end. This is already a valid BPMN diagram.

NewStart event, two tasks, end event, sequence flows.

Steps to draw it

  • 1. Place a start event on the left.
  • 2. Add tasks in the order the work happens.
  • 3. Finish with an end event that names the outcome.
  • 4. Connect them with solid arrows, left to right.

Why it matters

A process with one start and a named end tells the reader where it begins and how you know it is done. Naming the end state ("Refund issued", not "End") is the habit that separates clear diagrams from vague ones.

Level 2

Adding a decision

Real processes branch. An exclusive gateway sends the flow down exactly one path.

NewExclusive (XOR) gateway, labelled flows, a second end event.

Steps

  • 1. Insert a diamond with an X after the task that produces the answer.
  • 2. Write the question on the gateway: "Eligible?"
  • 3. Label every outgoing arrow with an answer.
  • 4. Give each outcome its own end event.

Why it matters

Separate end events show that "rejected" and "issued" are different outcomes, which makes reporting and testing far easier than a single shared end.

Pro note Every gateway answer must be mutually exclusive and cover all cases. If you cannot label the arrows "Yes/No" or with distinct values, the rule is not yet defined; that gap is a requirement to chase.
Level 3

Swimlanes: who does what

The same logic, now with responsibility. A pool is the process; lanes are the participants or roles inside it.

NewPool with three lanes: Customer, Customer Service, Finance.

Steps

  • 1. Draw one pool and split it into a lane per role.
  • 2. Move each task into the lane that performs it.
  • 3. Let arrows cross lane borders when work is handed over.
  • 4. Name lanes by role, not by person.

Why it matters

Swimlanes expose handovers, which is where delays and errors hide. Count the lane crossings: each one is a place to ask who owns the wait.

Pro note Sequence flow stays inside one pool; lanes are only partitions. When the customer is a separate organisation you do not control, model them as their own pool and connect with message flows (next level).
Level 4

Parallel work and messages

Some steps happen at the same time, and participants communicate. Both need their own symbols.

NewParallel gateways (split and join), a dashed message flow, extra tasks and end events.

Steps

  • 1. After approval, add a parallel split (diamond with +).
  • 2. Put the simultaneous tasks on separate branches.
  • 3. Close with a parallel join so the flow waits for every branch.
  • 4. Show the confirmation email as a dashed message flow to the customer.

Why it matters

A parallel split starts all branches; a parallel join waits for all of them. That wait is the difference between "refund done" and "refund done and order updated".

Pro note Match your splits and joins: an exclusive split closed by a parallel join deadlocks, and a parallel split closed by an exclusive merge runs the rest twice. If only some branches may run, use an inclusive (OR) gateway and join it with another.
Level 5

Exceptions and sub-processes

Production processes need deadlines, escalation and a way to hide detail without losing it.

NewNon-interrupting timer boundary event, escalation path, collapsed sub-process (the + marker).

Steps

  • 1. Attach a timer to the edge of "Review request": three days.
  • 2. Run an escalation path from the timer to a team lead.
  • 3. Make it non-interrupting (dashed ring) so the review continues.
  • 4. Collapse the detailed refund steps into one sub-process with the + marker.

Why it matters

Boundary events model exceptions on a task without cluttering the main flow. Collapsed sub-processes let one page stay readable while the detail lives in a linked diagram.

Pro note A solid ring timer interrupts the task and cancels it; a dashed ring runs in parallel. Choosing wrongly changes the business rule. Also prefer a boundary timer to a gateway that polls a date.

For experienced modellers

Conventions and common mistakes

Conventions that age well

  • Flow left to right; avoid crossing lines.
  • Verb-object for tasks, state for events, question for gateways.
  • Roughly seven to ten elements per diagram; collapse the rest.
  • Pick a modelling level on purpose: descriptive, analytic or executable.
  • Keep a naming glossary so the same step has one name everywhere.

Mistakes I see most

  • Gateways with unlabelled or overlapping answers.
  • Unmatched split and join types.
  • Sequence flow drawn between pools instead of message flow.
  • Lanes named after individuals or whole departments instead of roles.
  • Modelling every exception, burying the main path.
  • Dead ends: a branch with no end event.

If it must run in an engine

  • BPMN saves as XML with a diagram-interchange section for layout.
  • Add IDs, conditions and implementation details, which a descriptive model omits.
  • Camunda and Flowable run it; validate against the engine's supported subset.

BA habits that help

  • Walk the diagram with each lane owner and ask what is missing.
  • Trace one real case through it, including a failure.
  • Record the open business rules each gateway exposes.
Takeaways

What to take away

If you are new to BPMN

  • Start with events, tasks, gateways and arrows. That covers most diagrams.
  • Add detail one idea at a time, as these five levels did.
  • Name outcomes, not just steps.
  • Redraw rather than patch when a diagram gets messy.

If you already model

  • Match split and join types, and choose boundary events over polling.
  • Decide pool versus lane by who you control.
  • Use collapsed sub-processes to keep one page readable.
  • Treat each gateway as a requirement-gathering prompt.
